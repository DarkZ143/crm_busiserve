# Busiserve Enterprise CRM

Internal CRM and project operations workspace built with Next.js App Router, TypeScript, Firebase Authentication, Cloud Firestore, and the Firebase Admin SDK. The app starts with an empty database; it does not seed demo clients, employees, projects, prices, or work reports.

## Requirements

- Node.js 22 or newer
- A Firebase project for each environment (development and production)
- Firebase Authentication with Email/Password enabled
- A Firebase Admin service account or server runtime Application Default Credentials

## Local setup

1. Install dependencies with `npm ci`.
2. Create `.env.local` and set the Firebase values described below.
3. In Firebase Console, enable **Authentication → Sign-in method → Email/Password**. Do not enable public account creation in the application.
4. Deploy the Firestore rules and indexes with the Firebase CLI:

   ```bash
   firebase use YOUR_FIREBASE_PROJECT_ID
   firebase deploy --only firestore:rules,firestore:indexes
   ```

5. Add `localhost` and the production hostname to Firebase Authentication's authorized domains. For password reset links, also set `APP_ORIGIN` to the canonical application origin.
6. In Firebase Authentication, add the first administrator under **Users → Add user** and copy that account's UID.
7. In Firestore, create a document in the `users` collection with the document ID set to that exact UID. Add these fields as strings:

   | Field | Value |
   | --- | --- |
   | `uid` | The same Firebase Authentication UID |
   | `displayName` | The user's name |
   | `email` | The same email used in Firebase Authentication |
   | `role` | `super_admin` |
   | `accountStatus` | `active` |

8. Start the app with `npm run dev`, open `http://localhost:3000/login`, and sign in with that Firebase Authentication account. The `/setup` page shows these manual steps until a Super Admin profile exists.
9. Create accounts from **User management**. A Super Admin assigns each user ID, login email, role, and initial password. Share the initial password with the user securely; it is stored only by Firebase Authentication.

## Environment variables

| Variable | Purpose |
| --- | --- |
| `FIREBASE_PROJECT_ID` | Firebase project ID. |
| `FIREBASE_ADMIN_SERVICE_ACCOUNT` | Full Admin service-account JSON as a server-only environment variable. Alternatively use the three separate credentials below. |
| `FIREBASE_CLIENT_EMAIL` | Service-account email; used with `FIREBASE_PROJECT_ID` and `FIREBASE_PRIVATE_KEY` when not using the full JSON value. |
| `FIREBASE_PRIVATE_KEY` | Service-account private key; used with `FIREBASE_PROJECT_ID` and `FIREBASE_CLIENT_EMAIL` when not using the full JSON value. |
| `FIREBASE_API_KEY` | Firebase Web API key used by server routes for password sign-in, password reset, and Super Admin password confirmation before deleting a team member. It is not exposed to browser code. |
| `APP_ORIGIN` | Optional canonical origin for generated account recovery/setup links, e.g. `https://crm.example.com`. |
| `FIREBASE_USE_APPLICATION_DEFAULT` | Set to `true` only when the server runtime provides Application Default Credentials and `FIREBASE_PROJECT_ID` is set. |

Use either `FIREBASE_ADMIN_SERVICE_ACCOUNT` or the three separate values `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, and `FIREBASE_PRIVATE_KEY`. Never use a `NEXT_PUBLIC_` prefix for Admin credentials or the Firebase API key. Store production values in the hosting provider's secret manager. Give the service account only the Firebase roles required by the application and keep development and production projects separate.

## Roles and data access

- **Super Admin:** manages users, company settings, clients, projects, tasks, reports, and audit history. They approve or reject submitted clients and may assign an approved client to a Product Manager.
- **CTO, Product Manager, and Team Member:** can view only projects assigned to their role and submit client records for approval.

Every protected API route checks the session and role on the server. Non-Super Admin record queries are limited to assigned projects and the user's own client submissions. Business writes create audit records. Account suspension disables the Firebase Auth account and marks the Firestore user record inactive. Firestore browser/client SDK access is denied by `firestore.rules`; trusted server routes use the Admin SDK.

Core Firestore collections are `users`, `deletedUserIds`, `clients`, `projectRequests`, `projects`, `tasks`, `milestones`, `workReports`, `notifications`, `auditLogs`, `rateLimits`, and `companySettings`. Deleted user IDs are retired so historical records cannot become visible to a new account with a reused ID. The Super Admin assigns each user's authentication ID; other application record IDs are generated by the server. Dates are stored as Firestore timestamps or validated ISO date strings, and work dates use the company timezone (default `Asia/Kolkata`).

## Main workflows

1. Any non-Super Admin user can submit a client record. It remains pending and cannot be used for a project until approved.
2. A Super Admin reviews the client, approves or rejects it, and can assign an approved client to a Product Manager.
3. A Super Admin creates projects and assigns users. Each other user sees only the projects assigned to their role.
4. Super Admin user management records each account's user ID, login email, role, and access status. The initial password is never stored in the CRM profile. Deleting a team member requires the Super Admin's current password and allows five password attempts per hour.

## Routes

- Public: `/login`, `/forgot-password`, `/setup`
- Super Admin: `/admin/dashboard`, `/admin/users`, `/admin/clients`, `/admin/projects`, `/admin/tasks`, `/admin/reports`, `/admin/analytics`, `/admin/audit-logs`, `/admin/settings`
- CTO: `/cto/clients`, `/cto/projects`
- Product Manager: `/product-manager/clients`, `/product-manager/projects`
- Team member: `/workspace/projects`, `/workspace/clients`

## Validation and deployment

Run the local checks with:

```bash
npm test
npm run lint
npm exec tsc -- --noEmit
npm run build
```

Deploy the Next.js app to Vercel or another Node.js hosting platform. Configure the production environment variables in the host, set `APP_ORIGIN` to the public HTTPS origin, deploy Firestore indexes/rules to the matching production Firebase project, and add that hostname to Firebase Auth authorized domains. No database deletion or migration is run during deployment.

The included Vitest suite covers role access, record scoping, and redaction. Live Firebase authentication, Firestore rules, and production deployment must be verified against the actual Firebase project; this repository does not include project credentials. Password recovery calls Firebase Authentication directly. Initial passwords are set by a Super Admin and should be shared through an approved channel. Password reset email delivery depends on Firebase Authentication configuration; no SMTP provider is configured.

## Current operating limits

- List views retrieve up to 100 scoped records per collection, then provide local search, status filtering, and paging over that result. This should be replaced with cursor pagination and server-side search before collections grow beyond the cap.
- Search is currently local to each list; cross-collection global search and detailed client profile pages are not implemented yet.
- Analytics currently include live status counts and operational totals; there are no seeded values or revenue charts.
- Date filters, workload trend charts, and missing-report detection are not included yet.
- File uploads and external transactional email are not enabled.
- The current interface uses a temporary neutral palette and text wordmark until the Busiserve logo and official brand colors are supplied.
